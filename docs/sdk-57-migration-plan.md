# Migrazione a Expo SDK 57 — studio e piano (21/09/2026)

Stato: PIANO, nessuna modifica al codice applicativo. Sostituisce `docs/sdk-55-upgrade-plan.md` del branch `upgrade/expo-sdk-55` (fermo ad aprile, solo bump dipendenze).

## Decision Log

- **Contesto.** L'app è su SDK 54 (RN 0.81.5, React 19.1). Expo Go sull'App Store supporta solo l'SDK più recente (57); l'SDK 58 è in beta (RN 0.88) e Expo Go passerà al 58 poco dopo la stabile. Il test su iPhone con Expo Go è quindi bloccato.
- **Opzioni.** (A) restare su 54 e testare con development build / simulatore; (B) migrare a 57 e continuare con Expo Go; (C) saltare a 58 beta.
- **Scelta.** Migrare a **57** (B) *e* smettere di dipendere da Expo Go per i test seri (A): l'app usa moduli nativi che Expo Go non copre bene (maps, notifiche push, Sentry, updates). Non passare al 58 finché non è stabile: richiede Node 22+, iOS 27 con SceneDelegate, rework del core di expo-router e R8 di default.
- **Trade-off.** 3 SDK in un colpo (55, 56, 57) = più superficie di rischio; mitigato procedendo per gradini con verifica a ogni gradino. iOS minimo (vedi punto 12): da verificare a ogni gradino, non assumere 16.4 da SDK 56 senza controllo diretto (vedi correzione sotto).

## Requisiti degli store: cosa risulta oggi (VERIFIED su fonti ufficiali)

- **App Store:** dal 28/04/2026 gli upload richiedono Xcode 26 / SDK iOS 26. Expo dichiara SDK 54 e 55 già conformi (immagine EAS di default con Xcode 26). `eas.json` non fissa nessuna immagine → siamo conformi. **Nessuna urgenza store dall'SDK.**
- **Google Play:** dal 31/08/2026 nuovi app/aggiornamenti devono avere target API 36 (estensione richiedibile fino al 01/11/2026); le app esistenti devono targettare almeno API 35 per restare visibili. RN 0.81 usa `targetSdk = 36`, `compileSdk = 36`, `minSdk = 24` → conformi.
- Da SDK 56: Xcode ≥ 26.4. iOS minimo: **CORREZIONE (gradino 55→56, verificato su `node_modules/react-native/scripts/cocoapods/helpers.rb`)** — a RN 0.85.3 `min_ios_version_supported` è ancora **15.1**, non 16.4. L'assunzione iniziale era sbagliata (probabile confusione con un requisito Xcode/App Store, non con il deployment target dell'app). Da riverificare al gradino 56→57 (RN 0.86). Da RN 0.85: Node ≥ 20.19.4 (CI usa Node 20 → ok).

## Rischi specifici del nostro codice

1. **OTA / runtimeVersion (alto).** `runtimeVersion.policy = "appVersion"` con versione `1.0.0`: un OTA con codice SDK 57 pubblicato su un binario SDK 54 con la stessa versione lo manda in crash. Il workflow OTA parte a ogni push su `main`. Regola: nessun codice SDK 57 su `main` finché non esistono build 57; nel branch passare a `policy: "fingerprint"` (o bump di versione).
2. **NativeWind 2.0.11 -> 4.2.7 (RISOLTO — upgrade completato, gradino finale).** Spike senza device/emulatore disponibile (impossibile verificare bundle+render sul simulatore come previsto originariamente): fatto quanto verificabile senza device. Verificato via npm registry: `nativewind@4.2.7` dichiara esplicitamente supporto Expo SDK 57; `react-native-css-interop@0.2.7` (dipendenza interna) richiede `tailwindcss: "~3"` — NON va quindi bumpata a tailwindcss v4 (esiste, ma è per NativeWind v5, ancora in RC, fuori scope) — e `react-native-reanimated >=3.6.2` (soddisfatto da 4.5.1). Trovato prima di toccare codice: `global.css` esisteva già con le 3 direttive `@tailwind` ma non era importato da nessun file JS — con v2 non serviva (approccio babel-time senza CSS reale), con v4 è invece obbligatorio (Metro deve processarlo via `withNativeWind`) o nessuno stile si applica.

   Modifiche applicate: `package.json` (`nativewind` ^2.0.11 -> ^4.2.7, `tailwindcss` ^3.3.2 -> ^3.4.17); `babel.config.js` (`babel-preset-expo` con opzione `{ jsxImportSource: "nativewind" }` + `nativewind/babel`); `metro.config.js` (wrap con `withNativeWind(config, { input: './global.css' })`); `tailwind.config.js` (`presets: [require("nativewind/preset")]`); `app/_layout.tsx` (aggiunto `import "../global.css";` come prima riga del file — unico modo per far includere il CSS nel bundle).

   Bug reale trovato da `tsc` dopo l'upgrade (non preventivo): `components/Button.tsx` importava `styled` da `nativewind` (`styled(TouchableOpacity)`, `styled(Text)`) — API rimossa in v4. Root cause verificata sulla doc ufficiale: in v4 i componenti core RN (`View`, `Text`, `TouchableOpacity`, ecc.) supportano `className` nativamente grazie al babel jsxImportSource, `styled()` non serve più per loro (serve solo `cssInterop`/`remapProps`, e solo per componenti di terze parti — non è questo il caso). Fix: rimossi `styled`/`StyledTouchableOpacity`/`StyledText`, usati direttamente `TouchableOpacity`/`Text` con lo stesso `className`. Nessun altro file nel repo importa `styled` da `nativewind` (grep su tutto il codice applicativo). Pulizia collaterale: rimosso da `app/_layout.tsx` l'import morto di `StyleSheet` (residuo del fix `absoluteFillObject` del gradino 55->56, mai la causa di errori ma segnalato da eslint una volta toccato il file).

   Verificato: `tsc --noEmit` pulito, `eslint` pulito, `npm run test:regression` verde (nessun contract test copre nativewind/className, quindi è una verifica di non-regressione generale, non una prova di corretta resa a runtime). **NON verificato in questo ambiente, resta un rischio reale**: rendering visivo effettivo delle utility class su device/simulatore — l'utente non ha un device/emulatore disponibile ora e ha scelto esplicitamente di procedere comunque con l'upgrade e il merge, accettando questo rischio. Primo test visivo reale da fare appena disponibile un binario nativo o Expo Go aggiornato.

   **Secondo bug reale trovato, questa volta in CI (2026-09-22), non in locale**: dopo il push, il job "Type check" della CI falliva SEMPRE con `TS2882: Cannot find module or type declarations for side-effect import of '../global.css'` su `app/_layout.tsx` — ma `tsc --noEmit` passava sempre pulito in locale, anche ripetendo `rm -rf node_modules && npm ci` sullo stesso identico commit. Causa verificata riproducendo il fallimento in locale (rinominando temporaneamente `expo-env.d.ts`): l'unica dichiarazione `declare module '*.css'` di tutto il progetto viveva in `node_modules/expo/types/global.d.ts`, raggiunta solo tramite `expo-env.d.ts` — file GENERATO e in `.gitignore` (rigenerato in automatico da `npx expo`/dal dev server, mai committato). In locale capitava già rigenerato su disco da comandi precedenti in questa sessione, mascherando il problema ad ogni verifica; in CI (checkout pulito + `npm ci`, nessun comando Expo CLI prima di `tsc`) non esiste mai — da cui il fallimento sistematico, non un flake (confermato rilanciando il job: stesso errore, 11s). La catena di tipi di NativeWind (`nativewind/types` -> `react-native-css-interop/types`) NON fornisce questa dichiarazione, contrariamente a quanto assunto inizialmente: fa solo l'augmentation delle prop `className` sui componenti RN. Fix: aggiunta `declare module "*.css";` a `nativewind-env.d.ts` (file effettivamente tracciato in git, già incluso da `tsconfig.json` per la sua riga preesistente). Verificato con una controprova diretta: rimuovendo di nuovo `expo-env.d.ts` dopo il fix, `tsc` resta pulito. Aggiunto anche un contract test (`scripts/test_css_import_typing_contract.ts`, in `test:regression`) che verifica staticamente che la dichiarazione viva in un file tracciato in git — non in uno generato — per non ripetere lo stesso falso verde locale.
3. **`@react-navigation/*` (SECONDA CORREZIONE, questa volta verificata via Expo Go reale — la prima "correzione" al gradino 55→56 era sbagliata).** Testando il branch su Expo Go (SDK 57) l'app si è rifiutata di partire: `Error: As of SDK 56, expo-router is no longer compatible with react-navigation`. La mia analisi statica al gradino 55→56 (npm ls + grep sul codice di expo-router) mi aveva portato alla conclusione sbagliata che `@react-navigation/bottom-tabs` andasse tenuto. Causa vera, trovata leggendo il controllo effettivo in `node_modules/expo/node_modules/@expo/cli/build/src/start/server/metro/withMetroMultiPlatform.js` (righe ~592-609): Metro, quando `expo-router` è installato, blocca a livello di *resolver* qualsiasi import da `@react-navigation/*` fatto da codice applicativo (non da `node_modules`) — non è una questione di quale pacchetto sia installato, è un errore lanciato al momento della risoluzione dell'import stesso in `hooks/useBottomScreenInset.ts`. Fix ufficiale (verificata via https://docs.expo.dev/router/migrate/sdk-55-to-56/ e applicata con il codemod reale, non a mano): `npx expo-codemod sdk-56-expo-router-react-navigation-replace hooks/useBottomScreenInset.ts` → `import { BottomTabBarHeightContext } from "@react-navigation/bottom-tabs"` diventa `import { BottomTabBarHeightContext } from "expo-router/js-tabs"`. Verificato che `expo-router/js-tabs` esporta davvero `BottomTabBarHeightContext` (catena: `js-tabs.js` → `build/layouts/Tabs` → `export * from '../react-navigation/bottom-tabs'`, che contiene `BottomTabBarHeightContext`, `useBottomTabBarHeight`, ecc. — non un'assunzione, letto nei `.d.ts`). `@react-navigation/bottom-tabs` rimosso da `package.json` (era l'unico import `@react-navigation/*` in tutto il codice applicativo, grep su tutto il repo esclusi `node_modules`) e da `node_modules` (6 pacchetti rimossi con `npm install`, incluse le transitive `@react-navigation/native`/`core`/`elements`). tsc/eslint/regressione tornati verdi dopo la rimozione.
4. **Reanimated 4.1→4.5 / worklets 0.5→0.10 (VERIFICATO al gradino 56→57, rischio reale ma non un bug runtime).** Confermato: `babel-preset-expo` 57 inietta automaticamente `react-native-worklets/plugin` quando `react-native-worklets` è installato (`configs/expo.js`, `options.worklets !== false`), e il nostro `babel.config.js` elencava ANCHE esplicitamente `react-native-reanimated/plugin` — che a questa versione è solo un re-export di `react-native-worklets/plugin` (`node_modules/react-native-reanimated/plugin/index.js`). Quindi lo stesso plugin veniva eseguito due volte. Test diretto con `@babel/core` su un file reale (`hooks/useCardAnimation.ts`, usa `scale.value = withSpring(...)`) con e senza il plugin duplicato: nessun errore in entrambi i casi, output byte-per-byte identico (il plugin è idempotente) — quindi non era un bug silenzioso attivo, ma un doppio passaggio ridondante e non allineato alla guida ufficiale. Fix applicato: rimosso `react-native-reanimated/plugin` da `babel.config.js`, tenuto solo `nativewind/babel`; verificato via transform diretto che il worklet marker è comunque presente nell'output.
5. **Hermes V1 di default (SDK 56).** Regressioni di memoria e startup risolte in 57.0.9 / 57.0.17: partire da ≥ 57.0.24 (ok).

7. **expo-calendar (CORREZIONE: era "basso", in realtà ALTO — bug reale trovato e risolto al gradino 55→56).** Non è solo un warning: a SDK 56 l'import di default `"expo-calendar"` punta già alla nuova API a oggetti (`getCalendars`, `createCalendar`, classe `ExpoCalendar`, ecc.); i nomi classici usati da `utils/calendar.ts` (`getCalendarsAsync`, `getDefaultCalendarAsync`, `getCalendarPermissionsAsync`, `requestCalendarPermissionsAsync`, `createEventAsync`) esistono ancora nel default export ma sono stub che **lanciano un errore a runtime** (`build/legacyWarnings.js`, verificato riga per riga). Senza fix, "Aggiungi al calendario" si sarebbe rotto silenziosamente al primo build SDK 56+. Fix applicato: i due `await import("expo-calendar")` in `utils/calendar.ts` sono ora `await import("expo-calendar/legacy")`, che espone esattamente le stesse funzioni (verificato via `build/legacy/Calendar.d.ts`) — comportamento identico, nessun'altra modifica al file.

13. **`StyleSheet.absoluteFillObject` rimosso (ALTO — bug reale trovato e risolto al gradino 55→56).** Tra RN 0.83 e 0.85 l'export `absoluteFillObject` (l'oggetto di stile piatto, spreadabile: `{position:'absolute', left:0, right:0, top:0, bottom:0}`) è sparito sia dai tipi sia dal runtime di RN (resta solo `absoluteFill`, uno stile registrato non spreadabile — sostituirlo 1:1 avrebbe rotto silenziosamente il positioning). 3 usi trovati (`app/_layout.tsx`, `app/onboarding/npo-category.tsx` ×2, `components/GemmaAvatar.tsx`): tutti spread (`...StyleSheet.absoluteFillObject`) dentro altri stili. 14. **`eslint-plugin-react-hooks` v5→v7 via `eslint-config-expo` (medio, solo tooling — trovato e mitigato al gradino 55→56).** Il bump porta di default un nuovo blocco di regole "React Compiler readiness" (`react-hooks/refs`, `set-state-in-effect`, `preserve-manual-memoization`, `purity`, `immutability`, `static-components`): 114 errori lint su file mai toccati dalla migrazione. Verificato che il progetto non usa React Compiler (`app.json` non ha `experiments.reactCompiler`, `babel-preset-expo` lo attiva solo se esplicitamente configurato) → nessun impatto runtime, sono falsi positivi rispetto al nostro setup attuale (es. `react-hooks/immutability` marca come errore `sharedValue.value = ...` di Reanimated, che è l'API corretta e documentata). Le 6 regole nuove sono state disattivate in `eslint.config.js` con commento esplicativo; le regole classiche (`rules-of-hooks`, `exhaustive-deps`) restano attive. Decisione da riconfermare se in futuro si valuta di adottare React Compiler.
